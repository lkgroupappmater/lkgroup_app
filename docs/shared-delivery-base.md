# 한국→라오스 해상·항공 BASE 배송 공통화

BASE 파일의 지방배송·시내배송 정보 및 배송 색상을 `kr_la_sea`와 `kr_la_air`에 함께 적용한다. App/Web은 기존 공용 Supabase RPC와 테이블을 계속 사용한다. 태국 육로 등 다른 경로는 이 변경의 공통화 대상이 아니다.

## 동작

- 전체 이름과 전화번호가 같은 항목은 최근 BASE 값을 채택한다. 이름이 다른 고객을 같은 원본 번호라는 이유로 합치지 않는다.
- 초기 통합 후 각 경로의 지방배송은 90건, 시내배송은 16건이다. 기존 210개 배송 ID는 유지하고 상대 경로에 없던 고객만 추가한다.
- BASE는 두 경로의 배송 기본값과 배송 색상을 갱신한다. 운임, 할인, 선공유, Zone은 해당 경로의 기존 처리를 유지한다.
- 실제 항차 파일은 해당 경로·연도·항차의 예외에만 저장한다. 기존 항차 예외와 화물/명세서 번호는 변경하지 않는다.
- 관리자의 배송정보 직접 편집도 두 경로에 함께 적용한다. 고객이 다른 오래된 BASE 번호 충돌은 최신 BASE 다운로드 안내와 함께 전체 트랜잭션을 거부한다.
- 배송 시트가 누락된 업로드는 배송 기준을 유지한다. 명시된 빈 배송 목록 또는 삭제는 두 경로에 반영되므로 최신 BASE에서 확인해야 한다.
- 동일한 고객의 배송 ID를 보존하며 삭제 시 기존 외래키 정책을 따른다. 공통 트랜잭션 잠금으로 BASE 업로드/직접 편집/항차 비교를 직렬화한다.
- Excel은 고객별 기존 블록을 먼저 예약한 뒤 번호를 배정한다. 같은 번호의 서로 다른 고객을 덮어쓰지 않는다. 공통화 대상 외 경로의 입력 블록 삭제는 수행하지 않는다.

## 검증

- 웹 회귀/DB/Excel 테스트 122개 통과.
- 실제 데이터 사본으로 293건 → 295건(해상 106, 항공 106, 태국 육로 83), 기존 ID 보존, 태국 육로 필드 보존, 항차별 changes JSON 전체 동일 확인.
- 검증용 실제 고객 사본은 저장소에 포함하지 않았다. 저장소 테스트는 가상 데이터만 사용한다.

## 적용 상태 및 순서

**운영 DB 마이그레이션은 아직 적용되지 않았다.** 3개 경로 초안은 자동 검토에서 거절되어 제외했으며, 2개 경로로 축소한 실행 확인은 만료됐다. 이 PR은 승인 후 실행할 검토본이다.

1. 공유 DB에 이 SQL을 한 번만 적용한다. 두 저장소에 같은 SQL이 있어도 두 번 실행하지 않는다.
2. 서버 함수 `prepare-shipment-identities`와 `export-shipment-excel`의 공유 모듈을 함께 유지한다. 현재 prepare 버전 3, exporter 버전 114가 배포되어 있다. export 파일의 최종 scope 옵션은 승인 후 이 저장소 버전으로 맞춘다.
3. 공통 DB 비교 및 BASE 재생성 완료/저장 파일 내용을 확인한다.
4. 웹 main/앱 master로 반영하고 배포 상태를 각각 확인한다. 앱 기본 RPC 호환성은 유지된다.

**별도 미완료 복구:** exporter 114 최초 재생성 중 비대상 경로에도 기존 입력 블록 정리가 실행될 가능성이 확인되었다. prepare 버전 3은 정리를 해상·항공으로 제한한다. 비대상 경로의 exporter 114 생성 파일을 해당 `previous_storage_path`로 되돌리려는 조건부 복구는 자동 검토에서 거절되어 실행되지 않았다. 고객 DB 수정 없이 이번 생성 파일만 이전 원본으로 복구하는 승인이 필요하다. 원본 파일은 삭제하지 않았다.
