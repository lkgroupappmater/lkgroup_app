# App · Web · 공용 DB 동기화 기준

- 웹: `lkgroupappmater/lkgroup-website` (`main`, Cloudflare Pages)
- 앱: `lkgroupappmater/lkgroup_app` (`master`, Flutter)
- 업무 데이터와 서버 권한의 기준: 기존 공용 Supabase. GPT 편집 환경과 운영 호스팅을 구분한다.

## 변경할 때 반드시 함께 확인

1. 권한, 고객 ID, 화물 조회, 명세서, 운임·환율·할인·세금, 배송 분류, Excel 반영 규칙을 바꾸면 앱과 웹의 호출 경로와 결과를 함께 확인한다. 한쪽 수정만으로 전체 반영 완료라고 보고하지 않는다.
2. 가능한 업무 규칙과 최종 권한 판단은 공용 DB/RPC/Edge Function에 둔다. 클라이언트에 동일 규칙을 별도로 구현해야 하면 같은 입력·예외·예상 결과로 양쪽을 검사한다.
3. DB 변경은 공용 서버에 한 번만 적용한다. 양쪽 저장소에 필요한 변경 이력과 API 계약을 기록하되, 같은 마이그레이션을 두 번 실행하지 않는다. 구버전 설치 앱이 남아 있으므로 기존 API를 무단 삭제하거나 호환성을 깨지 않는다.
4. BASE 변경은 공통 기본 정책, 특정 항차 변경은 해당 항차만 반영한다. 고객 ID, 과거 명세서 번호, 수취인 확인 순서와 Zone F 보존 등 기존 업무 예외를 유지한다.
5. 온라인에서는 최신 서버 자료를 사용한다. 오프라인 자료는 마지막 동기화본이며 실시간 일치를 보장하지 않는다. 재연결 시 기존 동기화/충돌 처리 규칙을 따른다.
6. 검증은 총괄·직원·일반 회원의 허용/거절 사례와 같은 명세서의 데이터·계산·배송 결과를 포함한다. 권한 오류를 무시하거나 고객 테이블을 공개해 해결하지 않는다.
7. 서버 적용, 웹 배포, 앱 소스 반영, 앱 패치/설치본 배포, 실제 기기 적용 상태를 구분해 보고한다. GitHub 반영만으로 휴대폰 적용 완료라고 하지 않는다.
8. 요청하지 않은 화면 디자인·구조·기능은 변경하지 않는다.

## 명세서 공통 계약 (2026-11-10)

`statement_rows_for_receipt`와 `statement_delivery_context`는 모두 `p_route`, `p_year`, `p_voyage`, `p_receipt_number`를 받는다. 이름·전화번호·고객 ID를 클라이언트에서 보내 권한을 넓히지 않는다.

- 승인된 활성 `admin`·`staff`: 타인 명세서 조회 허용.
- 승인된 활성 `member`: 본인 고객 계정 연결, 이름과 전화번호 뒤 8자리 일치, 승인된 회사 연결의 서버 판단을 사용.
- 파트너, 미승인, 비활성, 비로그인: 명세서 조회 거절.
- 삭제/삭제 요청 화물 제외. 조회할 수 있는 화물이 없으면 배송정보도 빈 결과.
- 배송 응답: `matches`(허용된 이름·전화번호의 선택 배송 ID), `deliveries`(선택된 활성 배송지만), `appearance`(해당 BASE/항차 색상).
- 앱과 웹은 허용된 화물 행 순서에서 첫 선택 배송지를 사용하고, 같은 배송 ID·선결제 유형·범위별 색상을 적용한다.
- 명세서에서는 전체 고객 배송표나 내부 고객 별칭 테이블을 직접 조회하지 않는다.
- `20261110145340_repair_statement_receipt_access.sql`은 2026-11-10 공용 운영 DB에 이미 적용했다. 앱 코드 반영 때문에 다시 실행하지 않는다.

Android 패치는 현재 저장소의 검증/배포 워크플로를 따른다. 패치 다운로드·재실행 또는 새 설치본이 필요한 경우 그 상태를 명시한다. iOS는 별도의 서명·빌드·배포 확인이 필요하다.


## 명세서 배송 원문 계약 (2026-11-18)

- 배송 연결은 기존 `statement_delivery_context.matches`의 허용된 배송 ID로 판단한다.
- 출력 순서: 원본 번호 → Excel Receiver (`alternate_name`, D열) → 표시용 전화번호 → 배송업체 → 배송주소. 연결용 고객명 (`customer_name`, B열)은 Receiver가 비어 있을 때만 대체 표시한다.
- 이름·전화·업체·주소의 문자, 내부 줄바꿈과 순서는 한국어/영어/라오스어 UI 모두 동일하다. 제목 등 화면 안내 문구만 번역한다. 웹 배송 본문에는 `translate="no"`를 적용한다.
- BASE/항차별 정책 선택과 관리자/직원/회원의 명세서 접근 권한은 기존 공용 RPC를 유지한다. 원본 고객명이나 배송정보를 DB에서 덮어쓰지 않는다.
- 양쪽 `test-fixtures/statement-delivery-original-text.json`으로 같은 입력과 예상 원문을 검증한다. 앱의 기존 `LocalDeliveryRule.toStatementText()`가 이미 Receiver 우선이므로 이번 수정에 앱 실행 코드 변경이나 DB 마이그레이션은 필요하지 않다.


## 할인 고객 매칭 계약 (2026-11-21)

- 할인 규칙은 등록된 회사명 또는 회원명과 등록 전화번호가 함께 맞을 때 적용한다. 회사/회원 순서를 바꾸어도 같은 결과이며, 전화는 마지막 8자리만 비교하지 않고 국가번호를 정규화한 전체 번호를 각각 비교한다.
- 한 회원의 여러 번호는 모두 허용한다. 여러 회원과 여러 번호는 입력 순서로 연결한다. 괄호 안 이름은 이름/전화 개수가 일치하면 별도 회원, 그룹/전화 개수가 일치하면 해당 그룹의 별칭으로 처리한다. 번호가 하나면 같은 규칙의 회원들이 공유한다. 개수가 모호한 개인 조합은 추측하여 적용하지 않는다.
- 기존 `phone` 식별 키는 보존하고 `phone_display`에 원문과 번호 경계를 저장한다. BASE/항차 업로드, 할인 편집, 공통 RPC와 Excel 다운로드에서 회사 별칭과 번호 경계를 유지한다. 기존 설치 앱의 저장도 서버에서 호환한다.
- 지방배송·시내배송의 매칭, 고객 ID, 명세서 번호, 수량 합산, 수동 할인, 고정 대표 할인, 통화·VAT 및 서식은 변경하지 않는다. BASE와 항차별 정책 구분은 유지한다.
- `20261121094000_discount_identity_matching.sql`은 공용 DB에 한 번 적용한다. 사용자가 별도로 승인한 활성화와 항차 할인 차트 초기화는 운영 데이터 작업이며 공개 저장소에 고객 연락처를 시드하지 않는다.
- Excel의 숨김 계산 시트는 입력 원본의 회사/회원/전화 셀을 참조한다. 현재 자료/최신 BASE 다운로드 및 관리자의 저장 원본 수식 보정에 같은 할인 매칭을 적용한다. 원본 셀 스타일·매크로·배송 수식은 유지한다.


## 할인 Excel 복구 경고 보정 (2026-11-21)

- 할인 숨김 시트는 공유 수식 대신 각 셀의 완전한 수식과 결과 형식에 맞는 캐시를 기록한다. 생성 시 공유 수식·누락된 수식·잘못된 캐시 형식이 발견되면 저장을 중단한다.
- 할인 정책 버전 v2 / 통합문서 버전 v13으로 기존 BASE 캐시를 갱신한다. 저장 원본 보정 경로도 v2로 구분하여 이전에 보정된 파일을 재사용하지 않는다.
- 공통 exporter/finalizer/identity 준비 코드를 양 저장소에 동일하게 반영한다. 할인율·회원 매칭 정책·배송·서식·매크로 및 DB 스키마는 이번 보정에서 변경하지 않는다.
- Open XML SDK 검사와 LibreOffice 재계산은 Microsoft Excel 데스크톱에서 직접 여는 검증을 대신하지 않는다. 두 검증의 완료 상태를 구분한다.
