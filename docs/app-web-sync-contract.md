# App · Web · 공용 DB 동기화 기준

- 웹: `lkgroupappmater/lkgroup-website` (`main`, Cloudflare Pages)
- 앱: `lkgroupappmater/lkgroup_app` (`master`, Flutter)
- 업무 데이터와 서버 권한의 기준: 기존 공용 Supabase. GPT 편집 환경과 운영 호스팅을 구분한다.

## 변경할 때 반드시 함께 확인

1. 권한, 고객 ID, 화물 조회, 명세서, 운임·환율·할인·세금, 배송 분류, Excel 반영 규칙을 바꾸면 앱과 웹의 호출 경로와 결과를 함께 확인한다. 한쪽 수정만으로 전체 반영 완료라고 보고하지 않는다.
2. 가능한 업무 규칙과 최종 권한 판단은 공용 DB/RPC/Edge Function에 둔다. 클라이언트에 동일 규칙을 별도로 구현해야 하면 같은 입력·예외·예상 결과로 양쪽을 검사한다.
3. DB 변경은 공용 서버에 한 번만 적용한다. 양쪽 저장소에 필요한 변경 이력과 API 계약을 기록하되, 같은 마이그레이션을 두 번 실행하지 않는다. 구버전 설치 앱이 남아 있으므로 기존 API를 무단 삭제하거나 호환성을 깨지 않는다.
4. BASE 변경은 공통 기본 정책, 특정 항차 변경은 해당 항차만 반영한다. 고객 ID, 과거 명세서 번호, 수취인 확인 순서와 Zone F 보존 등 기존 업무 예외를 유지한다.
5. 온라인에서는 최신 서버 자료를 사용한다. 오프라인 자료는 마지막 동기화본이며 실시간 일치를 보장하지 않는다. 재연결 시 기존 동기화/충돌 처리 규칙을 따른다.
6. 검증은 총괄·직원·일반 회원의 허용/거절 사례와 같은 명세서의 데이터·계산·배송 결과를 포함한다. 권한 오류를 무시하거나 고객 테이블을 공개해 해결하지 않는다.
7. 서버 적용, 웹 배포, 앱 소스 반영, 앱 패치/설치본 배포, 실제 기기 적용 상태를 구분해 보고한다. GitHub 반영만으로 휴대폰 적용 완료라고 하지 않는다.
8. 요청하지 않은 화면 디자인·구조·기능은 변경하지 않는다.

## 명세서 공통 계약 (2026-11-10)

`statement_rows_for_receipt`와 `statement_delivery_context`는 모두 `p_route`, `p_year`, `p_voyage`, `p_receipt_number`를 받는다. 이름·전화번호·고객 ID를 클라이언트에서 보내 권한을 넓히지 않는다.

- 승인된 활성 `admin`·`staff`: 타인 명세서 조회 허용.
- 승인된 활성 `member`: 본인 고객 계정 연결, 이름과 전화번호 뒤 8자리 일치, 승인된 회사 연결의 서버 판단을 사용.
- 파트너, 미승인, 비활성, 비로그인: 명세서 조회 거절.
- 삭제/삭제 요청 화물 제외. 조회할 수 있는 화물이 없으면 배송정보도 빈 결과.
- 배송 응답: `matches`(허용된 이름·전화번호의 선택 배송 ID), `deliveries`(선택된 활성 배송지만), `appearance`(해당 BASE/항차 색상).
- 앱과 웹은 허용된 화물 행 순서에서 첫 선택 배송지를 사용하고, 같은 배송 ID·선결제 유형·범위별 색상을 적용한다.
- 명세서에서는 전체 고객 배송표나 내부 고객 별칭 테이블을 직접 조회하지 않는다.
- `20261110145340_repair_statement_receipt_access.sql`은 2026-11-10 공용 운영 DB에 이미 적용했다. 앱 코드 반영 때문에 다시 실행하지 않는다.

Android 패치는 현재 저장소의 검증/배포 워크플로를 따른다. 패치 다운로드·재실행 또는 새 설치본이 필요한 경우 그 상태를 명시한다. iOS는 별도의 서명·빌드·배포 확인이 필요하다.
